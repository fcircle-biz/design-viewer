# design-viewer

仕様書から、システムの全体像を 1 枚のキャンバスで見られるビューアを作る。
プロジェクト非依存なので、このフォルダーごと他のリポジトリへ持っていける。

| 表示モード | 内容 | 入力 |
|---|---|---|
| 概念図 | 人・仕組み・情報・外部ファイルの関係（属性なし） | `modes.concept` |
| 業務フロー | 横軸にアクター（担当者・システム）の列、縦軸に業務内容（フェーズ）の行をとった 1 枚のスイムレーン表に作業・分岐を並べ、上から下への流れを矢印で結ぶ | `modes.biz` |
| 機能一覧 | 全画面とバッチ機能の一覧（グループ別。バッチは画面の後ろのセクション）。`arrange: "table"` で 1 機能 1 行の表（サムネイル・ID・名称・概要・利用者／起動・実装状況）、既定はサムネイルの格子 | `screens`・`batches`（自動） + `modes.gallery` |
| 画面遷移図 | 画面モックアップを役割・チャネル別のレーンに並べ、遷移を矢印で結ぶ（`layout: "elk"` でレーン無しの全体 ELK 配置・カード・曲線。`arrange: "groups"` にするとハブ列＋グループ行の決定的な格子配置になる。20 画面超のハブ型向け） | `screens` + `modes.flow` |
| ER図 | テーブル・列・リレーション・多重度。テーブルも列も論理名と物理名を持たせ、図に描くのは論理名（物理名は詳細パネルの「列」表） | `modes.er` |
| データフロー | 外部・処理・データストアの流れ。ステップ再生つき（`arrange: "steps"` でステップごとのブロックに分けて描く。共有データストアが多い DFD 向け） | `modes.dfd` |
| ジョブフロー | バッチのジョブの順序。業務フローと同じスイムレーン表で、列に処理するシステム（サーバー）、行にバッチ（起動のタイミング）をとり、ジョブ・分岐を上から下へ並べる。正常終了の流れ・異常終了・再実行を線種で分ける | `modes.jobflow` |

メニュー（モード切替ボタン）は上表の順・名前が既定。変えたいときだけ `meta.modeOrder` と各モードの `label` で指定する（model.md §1）。

## 構成

```
.claude/skills/design-viewer/
  SKILL.md             この手順書
  schema/model.md      入力 model.json の仕様（必ず読む）
  engine/              ビューア本体（Canvas 2D。ビルドで出力先へコピーされる）
  engine/js/           ビューア本体の実体（01-core.js 〜 11-main.js。window.DV 名前空間で連携する）
  scripts/             build.js（validate → layout → thumbs → assemble）ほか
  scripts/vendor/      ELK.js（elkjs 0.12.0、EPL-2.0）
```

プロジェクト側:

```
<アプリ>/docs/spec/viewer-src/   入力（人・AI が書く）: model.json（または model/**/*.json）, screens/<ID>.html, screens/_shared.css
<アプリ>/docs/spec/html/         生成物（手で編集しない）: index.html を開けば見られる
```

`model.json` が肥大化する場合は、1 ファイルの代わりに `model/` ディレクトリ配下へ複数の
`*.json` に分割できる（`model.json` と `model/` は排他。両方あるとエラー）。分割方法・
マージ規則は [schema/model.md §1.1](schema/model.md#11-modeljson-の分割-model-ディレクトリ) を参照。

## 前提
- Node 18 以上。ELK は同梱なので npm install 不要。
- サムネイル生成に Playwright（リポジトリルートの `node_modules/playwright`）。無ければ thumbs をスキップし、画面は灰色の矩形になる。
  E2E 用などサブディレクトリにしか無い場合は `NODE_PATH=<そのディレクトリ>/node_modules node …/build.js …` で見つけられる。
- ビューアは file:// で動く（サーバー不要・外部 CDN 不要）。

## 手順

### 1. 仕様書を読んで範囲を決める
- 画面・バッチ・テーブル・フロー・登場人物を洗い出す。テーブルと列は**論理名（日本語）と物理名（DB 上の名前）を対にして**拾う（仕様書に片方しか無ければ、もう片方は書かず `info` / `note` に「未確定」と残す）。**仕様書に無いものを描かない。** 未確定の事項は `notes` / `info` / `meta.statusNote` に「未確定」と明記する。
- 画面をグループ（役割・チャネル・サブシステム）に分ける。1 グループ 6 画面を超えると折り返す。

### 2. `viewer-src/model.json` を書く
- 仕様は [schema/model.md](schema/model.md)。**座標は書かない**（レイアウトは自動。どうしても固定したいノードだけ `pin`）。
- 規模が大きい場合は並列に分担する: 画面メタと遷移 / バッチとジョブフロー / 概念図 / 業務フロー / ER 図 / データフロー を別々のエージェントに書かせ、最後に 1 つの JSON にまとめる。ID の命名（例: 画面 `S01`、バッチ `J01`、ジョブ `J01-1`・`JL_*`・`JP1`、業務フロー `B01`・`L_*`・`PH1`、DFD `P1`・`D1`）を先に決めておく。
  **モードをまたいで同じ ID を使うと、ビューアは同じノードとみなす**（種別が違うと片方が表示されない）。バッチの ID を業務フローの `B01` などと重ねない。
- 1 つの JSON にまとめる代わりに、`model.json` を作らず `viewer-src/model/` 配下へモード別
  （`model/modes/flow.json` など）にファイルを分けたまま出力してもよい。並列担当をそのまま
  ファイル単位に対応させられ、マージは `build.js`（内部の共通ローダー）が自動で行う。
  分割方法・マージ規則・ファイル名の数字接頭辞による順序制御は [schema/model.md §1.1](schema/model.md#11-modeljson-の分割-model-ディレクトリ) を参照。
- 画面遷移の方式を選ぶ: 役割・チャネルごとに帯で分けたいなら既定の `lanes`（ただし 60 画面規模では全体表示が
  読めなくなる。下記「既知の制約」参照）。画面数が少なく（〜20 画面程度）、ハブ型でなければ
  `modes.flow.layout: "elk"`（`docs/design-viewer-elk.html` の見た目。起点ノードは `attachTo`、段分けは
  `nudge` で調整する。model.md §4.1）。画面数が多く（20 画面超）、メニューなどの入口から多数の機能へ
  分かれるハブ型で、機能内に戻り・エラー遷移の循環があるなら `modes.flow.arrange: "groups"` ＋
  `hubGroup`（ELK を使わず、グループごとの行とハブ列に決定的に並べる。戻る遷移は `weak`、メニューへ
  戻る導線は `nav`、共通エラー画面への遷移は `rel` にして `toggles` で既定非表示にする。model.md §4.2）。
- データフローの方式を選ぶ: ノード 15 程度まで・共有データストアが少なければ既定（1 枚を ELK で配置）。
  受注テーブルのような共有データストアに多数のプロセスがつながる、または辺が 30 本を超えるなら
  `modes.dfd.arrange: "steps"`（すべての辺に `step` を付け、ステップごとに 外部実体 | プロセス | データストア の
  3 列のブロックで描く。共有ノードはブロックごとに複製される。model.md §6.3）。
- 業務フローは、`lanes` にアクター（人・部署・システム）を左から右へ、`phases` に業務内容を上から下へ、業務の順に並べる。
  関係の深いアクター（受け渡しの多い人とシステム）を隣り合わせにすると横に長い矢印が減る。差し戻し・戻りの辺は `type: "weak"` にする
  （段の決定から外れ、順方向の矢印と重ならない経路が選ばれる）。model.md §6.2。
- 機能一覧の方式を選ぶ: 画面の概要と実装状況を一覧で見せたいなら `modes.gallery.arrange: "table"` にし、全画面に
  `status`（`done` 実装済 / `wip` 実装中 / `designed` 設計済・未実装 / `planned` 未着手）と `purpose`（表の「概要」列。1〜2 文）を書く。
  実装状況は仕様書・リポジトリの実態（実装済みのコードがあるか、設計書だけか）から決め、推測で `done` にしない。
  サムネイルだけを大きく並べて見比べたいなら既定の格子（`grid`）。model.md §5。
- バッチ（画面を持たない定時・イベント起動の処理）は `batches[]` に 1 機能 1 件で書く（機能一覧の単位。例: 仕様書の機能一覧の「受注データ出力（バッチ）」）。
  `schedule`（起動のタイミング。表の「利用者／起動」列）・`trigger`・`status`・`purpose`・`ops`（処理の流れ）・`reads` / `writes`・`onError`（異常時）・`rerun`（再実行）を書く。
  異常時・再実行の方法が仕様書に無ければ `onError` / `rerun` を推測で埋めず、`notes` に「未確定」と書く。model.md §2.1。
- ジョブフローは `modes.jobflow` に、バッチを構成するジョブ（抽出 → 変換 → 出力 → 転送 など）の単位で書く。書き方は業務フロー（`modes.biz`）と同じで、
  `lanes` に処理するシステム・サーバー（外部システムを含む）、`phases` にバッチ（起動のタイミング）を置き、ノードの `batch` で `batches[].id` を参照する
  （詳細パネルから機能一覧のバッチへ移れる）。`variant` は `start | end | job | jobnet | wait | decision`、辺の `type` は
  `flow`（正常終了で次へ）| `ng`（異常終了時）| `weak`（再実行・戻り）。仕様書に異常時の分岐が無ければ `ng` の辺を描かない。model.md §6.4。
  ビューアの右上に「機能で絞り込む」セレクトボックスが出て、バッチ 1 件のジョブだけに絞れる。選択肢はノードの `batch` から作るので、
  **ジョブ（`start` / `end` を含む）には `batch` を付ける**。外部システム側の受け取りや分岐など `batch` を付けにくいノードは、
  そのバッチのジョブと同じ行（`phase`）に置けば一緒に表示される（1 バッチ 1 行にしておくと絞り込みと行が一致する）。
- 画面・バッチの `purpose / ops / reads / writes / notes / tasks / spec` は詳細パネルに出る。**ビューアの利用者は仕様書を手元に開いていない前提で書く。**
  `spec` には節番号（`§5.2` など）だけを書かず、関係する記述を「出典の名前: 転記した内容」の形で転記する
  （例: `"業務ルール（在庫）: 出庫によって在庫数が 0 未満になる場合はエラーとする。"`）。
  `notes` などの本文で出典を示すときも、番号ではなく節の名前（「（非機能要件）」など）で書く。

### 3. `viewer-src/screens/<ID>.html` を書く
- 1 画面 1 ファイルの完全な HTML 文書。`<div id="screen">` を `screens[].w × h`（既定 1440×900）で作り、共通 CSS は `_shared.css` に置いて相対リンクする。
- 一覧や明細の多い画面は 900px に収まらない。サムネイルは `w × h` で切り取られるので、Playwright で `#screen` の中身の実際の高さを測り、HTML の `#screen` の高さと `screens[].h` の両方に書く（最小 900）。
- 既存のモックアップ（1 ファイルに複数の状態を並べたもの等）がある場合は、作り直さずスクリプトで状態ごとに抜き出すと速い。外部 CDN 参照はローカルの CSS（例: アプリ本体の bootstrap.min.css を `_shared.css` にコピー）に置き換える。
- 画像ファイル・外部 CDN を使わない（アイコンはインライン SVG）。サンプルデータは架空にする。
- 画面が多い場合は、共通 CSS と部品の規約を先に決めてから画面ごとに並列で書く。

### 4. ビルド
リポジトリルートで:

```
node .claude/skills/design-viewer/scripts/build.js <アプリ>/docs/spec/viewer-src <アプリ>/docs/spec/html
```

- `--skip-thumbs` でサムネイル生成を飛ばせる（モックアップを変えていないとき。変更の無い画面はハッシュで自動スキップされる）。
- 各段階は単体でも実行できる: `validate.js <src>` / `layout.js <src> <out>` / `thumbs.js <src> <out>` / `assemble.js <src> <out>`。
- validate がエラー（未知 ID を参照する辺、ER の存在しない列、重複 ID など）を出したら model.json を直して再実行する。
- assemble は出力先の**無関係な既存ファイルを削除しない**。古い生成物が残っていたら人が判断して消す。

### 5. 目で確認する
- `<アプリ>/docs/spec/html/index.html` を開き、全モード（キー 1〜7。データのあるモードだけボタンが出る）を全体表示（F）で見る。ツールバーが 1 行に収まっているかも見る（「ツールバー」節）。
- **自動レイアウトは万能ではない。** 読みにくい箇所は次の順で対処する:
  1. model.json の並び順を変える（ELK は記述順をある程度尊重する）
  2. グループ分けを見直す（1 グループに詰め込みすぎない）
  3. 辺ラベルを短くする（長いラベルは重なりの原因）
  4. それでも駄目なノードだけ `pin` で固定する
- Playwright で確認する場合は、`window.__viewerPerf.frames`（直近の描画時間 ms）で性能も見られる。

## ビューアの操作
ドラッグで移動、ホイールで拡大縮小、F で全体表示、1〜7 でモード切替、`/` で検索、ダブルクリックでノードに寄る、
クリックで詳細パネル（ジョブの［関連バッチ］・バッチの［ジョブフロー］の行をクリックすると機能一覧 ⇔ ジョブフローを切り替えてそのノードに寄る）、詳細パネルの左端をドラッグして幅を変更（ダブルクリックで既定幅 560px に戻る。
幅は次回開いたときも保持する）、詳細パネルの［画面を開く］で等倍プレビュー、［近傍のみ］（ツールバーのノード網アイコン）で選択ノードの隣接だけ表示、
右下のミニマップで移動（詳細パネル表示中に可視領域が狭いと自動的に隠れる）、ツールバーの［概要］（i アイコン）［凡例］（リストアイコン）で左上のシステム概要カード・左下の凡例カードの表示／非表示を切り替え（図の上に重なるカードを隠して広く見る。状態はブラウザの localStorage に保存し、次回開いたときも保持する）、グループ見出しクリックでそのグループに寄る（業務フローはフェーズ見出しでその行に寄る。アクター・フェーズの見出しは画面の上端・左端に貼り付く）、
データフローは右上のステップで段階ごとに強調（`arrange: "steps"` ではそのステップのブロックへ寄る）、
ジョブフローは右上の「機能で絞り込む」でバッチ 1 件のジョブだけを表示してその行へ寄る（ほかのバッチの行は取り除いて上へ詰め、検索・ミニマップ・［近傍のみ］も絞り込んだジョブだけが対象。
選択はモードを切り替えても保持する。隠れているジョブへ検索などで寄ると絞り込みを解除する。バッチの詳細パネルの［ジョブフロー］から移るとそのバッチで絞り込む）。

### ツールバー（画面下のメニュー）
**1 行に収める**（2 段に折り返すと図の下端を大きく隠すため）。幅 1024px 以上の画面で 1 行になることを保つ。

| 並び | 部品 | 表示 |
|---|---|---|
| 1 | モード切替（概念図〜ジョブフロー。最大 7 つ） | 文字のタブ（`.v-seg-btn`）。見分けるのに名前が要るので文字のまま |
| 2 | 近傍のみ | アイコン（点を線でつないだ図）。オンで青地 |
| 3 | 概要・凡例の表示切替 | アイコン（ⓘ・リスト）。表示中は青地 |
| 4 | 縮小・倍率・拡大・全体表示 | アイコン（− ＋ 四隅のカギ括弧）と倍率の数字 |

- モード切替以外はアイコンボタン（`engine/index.html` の `.v-tool-btn`。30×30px・枠なし・インライン SVG の 18px 線画）にする。
  名前は `title`（マウスを載せると出るツールチップ。ショートカットキーがあれば「全体表示（F）」のように添える）と `aria-label` に書く。
- トグル（オン／オフのあるボタン）は `.v-active` で青地に白、`aria-pressed` も合わせて切り替える。
- ボタンを足すときも同じ作り（アイコン＋`title`＋`aria-label`、`.v-tool-btn`）にし、文字ボタンを足さない。区切りは `.v-toolbar-sep`。
- `#toolbar` は `flex-wrap:nowrap`。1 行に収まらないのは、詳細パネルを開いて可視領域が狭いとき（`body.v-panel-narrow`。
  09-panel.js の `updateToolbarLayout` が重なりを実測して付ける）と、幅 720px 以下のモバイルだけで、そのときだけ折り返す。
- `meta.modeOrder` と各モードの `label` でモード名を変えるときは、長い名前にしない（タブの幅がそのままツールバーの幅になる。
  既定の 6 モードでツールバー全体が約 740px、ジョブフローを加えた 7 モードで約 835px）。
- 手順 5 で見るときは、1280px と 1024px の幅でツールバーが 1 行に収まることも確かめる。

## 性能の目安（2026-09-15 実測。1600×1000・DPR 2・ヘッドレス Chromium）
- 待機中の描画: 0 回（状態が変わったときだけ描く）
- 12 画面の実データ: 1 フレーム p50 0.7ms / p95 1.9ms
- ダミー 100 画面・50 テーブル・400 辺: p95 おおむね 5〜9ms
- レイアウト計算: 実データ 0.5 秒、ダミー 2 秒前後

性能が落ちたら、まず `engine/js/` の描画（06-render.js・07-draw-groups-edges.js・08-draw-nodes.js など）が**ワールドに HTML 要素を置いていないか**（置くと拡大縮小のたびに再ラスタライズされて破綻する。v1 がこれで使えなかった）を確認する。

## 既知の制約
- 機能一覧の表（`arrange: "table"`）は画面数に比例して縦に長くなり（66 画面で約 12,000px）、全体表示は表の上端しか見せない。下の画面は検索（`/`）で寄るか、ドラッグ・ミニマップで移動する。
- 機能一覧（格子）・レーンの画面名（ID とタイトル）は、サムネイルが画面上で 90px 未満の縮尺では描かない（はみ出して隣と重なるため）。全体表示で画面名が出ないときは拡大するか、グループ見出しをクリックしてそのグループに寄る。
- ER図は FK 側を東、参照先を西のポートに接続するため、循環参照が多いと辺が左に回り込むことがある。
- 業務フローの段（フェーズ内の上下の位置）はフェーズ内の最長経路順で決まるため、フェーズのノードが一直線に続くほど行が縦に長くなる。フェーズ・ノードが多いと表全体が縦長になり、全体表示ではノードの文字が読めない（実データ 6 アクター・6 フェーズ・42 ノードで 2656×5944、全体表示 14%）。全体表示は構造の把握用とし、フェーズ見出しをクリックして行へ寄って読む。1 フェーズ 7 ノード程度を目安に分ける。
- 業務フローで分岐の行き先が同じアクターに複数あると、同じセルに横に並ぶためそのアクターの列が全フェーズで広がる。ルートは直交で他ノード・既存の辺を避ける候補から選ぶが、辺が多いと通路で並走することがある。
- 画面遷移のレーン内は位相順の 1 行配置（6 画面超で折り返し）。レーンをまたぐ辺はレーン下の通路を回る。`lanes` は 60 画面規模だと全体表示で読めない（1 レーンが縦に長くなりすぎる）。20 画面を超えるハブ型は `arrange: "groups"` を検討する。
- `layout: "elk"` の曲線はノードを避けないため、辺の多いグラフでは交差・ノード横断が増える。`nudge` は ELK の結果を見てから決める（起点を `attachTo` にしないと層がずれて補正量が合わなくなる）。戻る遷移は `type: "weak"` にして層の決定から外す。それでも長い辺がカードを横切るハブ型の遷移は、全画面を `pin` で格子に置く（model.md §4.1）か、`arrange: "groups"` を使う（model.md §4.2）。
- `arrange: "groups"` の曲線もカードを避けないので、段を飛ばす辺（一覧 → 登録入力など）は間のカードの上を通ることがある。また、ハブ列から 2 本目以降のブロック列にあるブロックへ向かう辺は、1 本目のブロック列にあるブロックの上を横切る（ブロックは記述順に列へ振り分けられるため）。ビューアの［近傍のみ］で選択画面の辺だけに絞ると追いやすい。
- データフローを 1 枚（既定）で配置すると、共有データストアに多数のプロセスがつながる図では長い辺が図全体を横切って読めない（29 ノード・60 辺で交差 52）。`arrange: "steps"` を使う。その場合、同じノードが複数ブロックに出るため検索結果に同じ名前が並ぶ。また列が固定なので、同じ列どうしの辺（proc → proc など）は曲線が大きく回り込む。
- ツールバーは幅 1024px 程度の画面では 1 行に収まるが、左下の凡例カード・右下のミニマップと端が重なる（7 モードで約 835px のため、6 モードのときより重なりが大きい）。凡例カードはツールバーの凡例ボタンで隠せる。
- ジョブフローは業務フローと同じ配置なので、業務フローの制約（段の決定・同じセルに横に並ぶと列が広がる）がそのまま当てはまる。
- ジョブフローの機能の絞り込みは、ビューアで対象外の行を取り除いて詰めるだけで、レイアウトは作り直さない。そのため、1 つの行に複数のバッチのジョブを置くと、
  絞り込んでも列の幅・行の高さは全バッチ分のままで、選んでいないバッチのジョブの位置は空白になる。また、バッチをまたぐ辺（先行バッチの終了 → 後続バッチの起動など）は、両端が表示されているときだけ描く。
- バッチ機能にはサムネイルが無いので、機能一覧の格子では時計のアイコンと名称・起動のタイミングを描いたカード（画面と同じ 1440×900）になる。
- 大きな ER テーブルを極端に拡大すると、キャッシュの画素数上限により文字がわずかに甘くなる。
- `pin` したノードは重なり回避の対象外。
