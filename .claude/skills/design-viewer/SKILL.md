# design-viewer

仕様書から、システムの全体像を 1 枚のキャンバスで見られるビューアを作る。
プロジェクト非依存なので、このフォルダーごと他のリポジトリへ持っていける。

| 表示モード | 内容 | 入力 |
|---|---|---|
| 画面遷移 | 画面モックアップを役割・チャネル別のレーンに並べ、遷移を矢印で結ぶ（`layout: "elk"` でレーン無しの全体 ELK 配置・カード・曲線） | `screens` + `modes.flow` |
| 画面イメージ | 全画面のサムネイル一覧（グループ別） | `screens`（自動） |
| 概念図 | 人・仕組み・情報の関係（属性なし） | `modes.concept` |
| ER 図 | テーブル・列・リレーション・多重度 | `modes.er` |
| データフロー | 外部・処理・データストアの流れ。ステップ再生つき | `modes.dfd` |

## 構成

```
.claude/skills/design-viewer/
  SKILL.md             この手順書
  schema/model.md      入力 model.json の仕様（必ず読む）
  engine/              ビューア本体（Canvas 2D。ビルドで出力先へコピーされる）
  scripts/             build.js（validate → layout → thumbs → assemble）ほか
  scripts/vendor/      ELK.js（elkjs 0.12.0、EPL-2.0）
```

プロジェクト側:

```
<アプリ>/docs/spec/viewer-src/   入力（人・AI が書く）: model.json, screens/<ID>.html, screens/_shared.css
<アプリ>/docs/spec/html/         生成物（手で編集しない）: index.html を開けば見られる
```

## 前提
- Node 18 以上。ELK は同梱なので npm install 不要。
- サムネイル生成に Playwright（リポジトリルートの `node_modules/playwright`）。無ければ thumbs をスキップし、画面は灰色の矩形になる。
- ビューアは file:// で動く（サーバー不要・外部 CDN 不要）。

## 手順

### 1. 仕様書を読んで範囲を決める
- 画面・テーブル・フロー・登場人物を洗い出す。**仕様書に無いものを描かない。** 未確定の事項は `notes` / `info` / `meta.statusNote` に「未確定」と明記する。
- 画面をグループ（役割・チャネル・サブシステム）に分ける。1 グループ 6 画面を超えると折り返す。

### 2. `viewer-src/model.json` を書く
- 仕様は [schema/model.md](schema/model.md)。**座標は書かない**（レイアウトは自動。どうしても固定したいノードだけ `pin`）。
- 規模が大きい場合は並列に分担する: 画面メタと遷移 / 概念図 / ER 図 / データフロー を別々のエージェントに書かせ、最後に 1 つの JSON にまとめる。ID の命名（例: 画面 `S01`、DFD `P1`・`D1`）を先に決めておく。
- 画面遷移の方式を選ぶ: 役割・チャネルごとに帯で分けたいなら既定の `lanes`。画面数が少なく（〜20 画面程度）、
  画面のつながりを 1 枚の流れ図として見せたいなら `modes.flow.layout: "elk"`（`docs/design-viewer-elk.html` の見た目。
  起点ノードは `attachTo`、段分けは `nudge` で調整する。model.md §4.1）。
- 画面の `purpose / ops / reads / writes / notes / tasks / spec` は詳細パネルに出る。仕様書の節番号・タスク ID を入れておくと追跡しやすい。

### 3. `viewer-src/screens/<ID>.html` を書く
- 1 画面 1 ファイルの完全な HTML 文書。`<div id="screen">` を `screens[].w × h`（既定 1440×900）で作り、共通 CSS は `_shared.css` に置いて相対リンクする。
- 画像ファイル・外部 CDN を使わない（アイコンはインライン SVG）。サンプルデータは架空にする。
- 画面が多い場合は、共通 CSS と部品の規約を先に決めてから画面ごとに並列で書く。

### 4. ビルド
リポジトリルートで:

```
node .claude/skills/design-viewer/scripts/build.js <アプリ>/docs/spec/viewer-src <アプリ>/docs/spec/html
```

- `--skip-thumbs` でサムネイル生成を飛ばせる（モックアップを変えていないとき。変更の無い画面はハッシュで自動スキップされる）。
- 各段階は単体でも実行できる: `validate.js <src>` / `layout.js <src> <out>` / `thumbs.js <src> <out>` / `assemble.js <src> <out>`。
- validate がエラー（未知 ID を参照する辺、ER の存在しない列、重複 ID など）を出したら model.json を直して再実行する。
- assemble は出力先の**無関係な既存ファイルを削除しない**。古い生成物が残っていたら人が判断して消す。

### 5. 目で確認する
- `<アプリ>/docs/spec/html/index.html` を開き、5 モード（キー 1〜5）を全体表示（F）で見る。
- **自動レイアウトは万能ではない。** 読みにくい箇所は次の順で対処する:
  1. model.json の並び順を変える（ELK は記述順をある程度尊重する）
  2. グループ分けを見直す（1 グループに詰め込みすぎない）
  3. 辺ラベルを短くする（長いラベルは重なりの原因）
  4. それでも駄目なノードだけ `pin` で固定する
- Playwright で確認する場合は、`window.__viewerPerf.frames`（直近の描画時間 ms）で性能も見られる。

## ビューアの操作
ドラッグで移動、ホイールで拡大縮小、F で全体表示、1〜5 でモード切替、`/` で検索、ダブルクリックでノードに寄る、
クリックで詳細パネル、詳細パネルの［画面を開く］で等倍プレビュー、［近傍のみ］で選択ノードの隣接だけ表示、
右下のミニマップで移動、グループ見出しクリックでそのグループに寄る、データフローは右上のステップで段階ごとに強調。

## 性能の目安（2026-09-15 実測。1600×1000・DPR 2・ヘッドレス Chromium）
- 待機中の描画: 0 回（状態が変わったときだけ描く）
- 12 画面の実データ: 1 フレーム p50 0.7ms / p95 1.9ms
- ダミー 100 画面・50 テーブル・400 辺: p95 おおむね 5〜9ms
- レイアウト計算: 実データ 0.5 秒、ダミー 2 秒前後

性能が落ちたら、まず `engine/viewer.js` の描画が**ワールドに HTML 要素を置いていないか**（置くと拡大縮小のたびに再ラスタライズされて破綻する。v1 がこれで使えなかった）を確認する。

## 既知の制約
- ER 図は FK 側を東、参照先を西のポートに接続するため、循環参照が多いと辺が左に回り込むことがある。
- 画面遷移のレーン内は位相順の 1 行配置（6 画面超で折り返し）。レーンをまたぐ辺はレーン下の通路を回る。
- `layout: "elk"` の曲線はノードを避けないため、辺の多いグラフでは交差・ノード横断が増える。`nudge` は ELK の結果を見てから決める（起点を `attachTo` にしないと層がずれて補正量が合わなくなる）。戻る遷移は `type: "weak"` にして層の決定から外す。それでも長い辺がカードを横切るハブ型の遷移は、全画面を `pin` で格子に置く（model.md §4.1）。
- 大きな ER テーブルを極端に拡大すると、キャッシュの画素数上限により文字がわずかに甘くなる。
- `pin` したノードは重なり回避の対象外。
